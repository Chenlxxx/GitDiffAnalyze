# 使用方仓库多层调用链路追踪（第 4 步详细方法）

当工作目录是使用该三方库的代码仓库时，本文件指导如何把上游风险项落到真实代码上。
核心：**不要只搜一层直接调用**，要追踪从「上游变更 API」到「业务入口」的完整链路。这是 compat-analyze 区别于“只看上游 changelog”的核心价值。

## 前置
1. 确认仓库确实依赖该库、依赖的是哪个版本（读 `pom.xml` / `build.gradle*` / `package.json` / `go.mod` / lockfile）。若版本与分析的目标版本不一致，在报告中说明。
2. 对每条上游风险项，取出它的受影响 API 符号（类/接口/方法/字段/配置项名）。

## 逐项追踪步骤

### a. 定位直接使用点
搜索对受影响 API 的直接引用，覆盖多种形式：
- import / use / require
- `new` 实例化、静态方法调用、字段访问
- 继承（extends）、实现（implements）、重写（@Override）
- 注解使用（如该 API 是注解）
- 配置文件 / XML / YAML / properties 中出现的类名或配置键

用精确符号名搜索；找不到直接命中再用更宽的关键词（包名、简单类名）。

### b. 向上追踪调用链
找到直接使用点后，继续追踪**谁调用了它们**，一层层向上，直到业务入口：
- 包装类(wrapper)、适配器(adapter)、门面(facade)、工具类(util)、基类(base)、抽象层
- 直到：Controller / RPC 接口 / Service 公开方法 / 定时任务 / 消息消费者 / CLI 入口 / 对外 SDK 方法

为每条命中项画出链路：`上游变更 API → 本仓库封装层(具体文件:类:方法) → 业务入口(具体文件:类:方法)`。

### c. 覆盖间接 / 隐式使用
纯文本搜索容易漏掉这些命中方式，逐一排查：
- 反射（`Class.forName`、`getMethod`、动态调用）
- SPI / ServiceLoader（`META-INF/services`）、插件机制
- 依赖注入（Spring Bean、`@Autowired`、`@Resource`、构造注入、XML bean 定义）
- AOP 切面 / 拦截器 / 动态代理
- 配置驱动实例化（类名写在配置里）
- 字节码增强 / agent / 序列化框架（Jackson、Gson、protobuf 等对字段/构造的隐式依赖）

### d. 识别运行时故障面
判断该变更：
- 在**编译期**暴露（签名变化、删除的方法）——升级即编译失败，相对安全（看得见）；
- 还是仅在**运行时**暴露（默认行为变化、序列化格式变化、更严格校验）——编译通过但线上出问题，**风险更高**，需指出触发场景与可能的报错特征。

### e. 给出结论
基于以上证据，把该风险项**确认 / 降级 / 推翻**：
- 确认成立：给出完整调用链、受影响业务入口、故障模式、整改建议。
- 降级/不适用：说明仓库为何不受影响（未使用该 API、有隔离封装、走了其他分支等）。
- 无法判定：放入「待人工确认问题」，写清缺什么信息。

## 输出
把结论合并进 `compat-report.md` 的「本仓库命中情况」一节（见 report-template）。对每条命中项务必给出**完整调用链**与**受影响业务入口**，而不仅是“某文件用到了某 API”。
