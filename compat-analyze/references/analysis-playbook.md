# 分级分析策略与风险定级准则

本文件是 compat-analyze 第 2 步的详细规则，对齐 CompatAnalyzer 平台的分析逻辑。

## 一、按变更规模选择策略

用 `compare` 返回的文件数（`files` 长度）与 commit 数决定：

| 规模 | 策略 | 做法 |
|---|---|---|
| ≤ 50 文件 | 完整 Diff 分析 | 通读整体 diff，逐文件、逐变更点分析 |
| 50 – 1000 文件 | 分组分批分析 | 按目录/功能分组，组内按优先级排序后分批精读 |
| > 1000 文件 或 diff 不可用 | 概览分析 | 基于 commit 列表 + 变更日志归纳，**报告中标注未做源码级验证** |

### 文件优先级（分组分批时）
精读顺序从高到低：
1. **核心源码**：公开 API、核心类/接口实现（`src/main`、`lib/`、`core/` 等）
2. **接口/协议/配置**：公开接口定义、协议/序列化、默认配置项、SPI 描述符（`META-INF/services`）、注解处理器
3. **构建与依赖**：`pom.xml` / `build.gradle` / `package.json` 的依赖与版本约束变化（尤其最低运行环境提升）
4. **测试**：通常只扫文件名与新增/删除的测试名（能反推行为变化），不逐行精读
5. **文档**：只扫标题，除非是迁移指南/升级说明

大 diff 时：高优先级文件读完整 patch，低优先级只看文件名与增删行数。

## 二、风险定级准则

- **High（破坏性，必须处理）**
  - 公开 API 删除 / 方法签名变更 / 返回类型或语义变更
  - 默认行为变化（默认值、默认开关、默认策略）
  - 配置项删除或默认值变化
  - 序列化格式 / 协议 / 线格式（wire format）变化
  - 依赖的最低运行环境提升（JDK、Node、Python 版本等）
  - 异常类型变化（抛出的异常类/错误码改变）

- **Medium（需关注）**
  - 公开 API 标记 `@Deprecated`（尚可用但将移除）
  - 新增的更严格校验（原本宽松的输入现在会被拒）
  - 性能特征明显变化（复杂度、内存、连接池默认值）
  - 内部类/protected 成员变更，但常被反射或继承使用

- **Low（基本无影响）**
  - 纯新增功能（不影响既有调用）
  - 内部重构（不改变公开行为）
  - 文档、注释、测试变更

整体风险 = 取所有风险项的最高级别。

## 三、每条风险项的质量要求

不要一句话敷衍。每项尽量写充分、具体：
- **变更说明**：改了什么、为什么改；**点名**受影响的类 / 接口 / 方法 / 字段 / 配置项的具体名称（如 `com.foo.Bar#doX(String)`）。
- **受影响 API 列表**：列出公开 API 全名，便于在使用方仓库里搜索。
- **兼容性影响**：使用方在什么调用场景会受影响；在**编译期**暴露还是仅**运行时**暴露；如何排查。
- **迁移/整改建议**：具体步骤；High/Medium 项尽量给 before/after 代码示例。
- **证据**：引用关键 diff 片段 / commit SHA / 变更日志原文。**严禁脱离证据臆测**；批次失败或未覆盖的部分如实标注，不要编造。

## 四、分批分析时的聚合
分批分析后做一次汇总：合并重复或同类变更点、融合各批最具体的描述与证据、按风险降序排列。汇总时不要为精简而丢失关键技术细节（受影响 API、迁移步骤、代码示例都要保留）。
